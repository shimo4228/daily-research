**取得の制約（T7・T8 の取得で 2026-11-08 に観察）。** WebFetch は長いページを約 100,000 字で切り、原文の引用も短く切って
要約で返す。2026-11-06 の wide の本番の呼2 は 114,780 字の HN スレッドを途中までしか読めず、実在する発言を「該当する発言がなかった」として削った（正しい文を消した誤訂正）。
監査側も同じ上限を持ち、試作は HN の item 単体の URL や `offset` 付きの 2 回目の取得で届かせていた。

**権限の制約。** Claude Code の permission 規則は deny → ask → allow の順に評価され、allow は deny に例外を作れない

開け直せない。監査の cwd は daily-research で、ノートは cwd の外の vault にあるので、この経路でも書けない。

## Decision

1. **呼3（照合監査）を足した。** `[audit] enabled`（コードの既定 false）のとき、各 line の呼2 の後に kind: article の
   ノートだけを監査する（brief は対象外。呼2 が失敗して未検証のノートも監査する）。`[audit] model` の既定は opus
   （設定キーの説明は `config.example.toml`）。起動（`scripts/daily-research.sh` の `audit_call`）は呼1・呼2 と同じ
   `--safe-mode`・`--permission-mode default`・`--output-format json` で、道具の集合を `--tools WebFetch` にし（WebSearch は
   呼2 と同じく deny）、`--effort high` を足した。`--effort` は、効く値を記録の残る形で固定するために明示した（試作は付けず効いた値が
   分からない。T9 は high で測った）。
2. **2 段にし、両段が食い違いとした候補だけを確定にした。** 第 1 段（`prompts/audit-protocol.md`、`--max-turns 40`、
   外側の timeout 600 秒）はノート本文の主張を原典で確かめ、原典と両立しない文だけを JSON で返す（ノートの文を
   一字一句写した文・25 語以内の原典の引用・ノートに書かれた URL・実際に読んだ URL・URL を含まない文書内の位置
   （locator）・正しい値・最小の置き換え文・型・確信度・drift）。「取得したページに
   無い」は根拠でなく unverifiable として数えるだけにした。WebFetch への依頼は値を問う形で書きノートの値を書かない、
   2 つの取得が食い違えば範囲の狭い URL を採る、指示語で始まる文は指す先の文から写す、の 3 規則は T9 の 1 回目の
   見逃しを受けて 2 回目の前に足した（第 2 段のプロトコルには前の 2 つ）。第 2 段（`prompts/audit-confirm-protocol.md`、`--max-turns 20`、240 秒）は候補ごとに別の呼び出しで、ノートの文（文 A）・
   第 1 段の置き換え文（文 B）・URL・locator・ノートの公開日を受け取り、A が原典と両立するか（`verdict`）と B が原典と
   両立するか（`replacement_verdict`）を判定し、誤りの部分と訂正の部分を A・B から逐語で写す（`parts` の `wrong` /
   `fixed`、削除の訂正は `fixed` を空にする）。第 1 段の理由・正しい値は渡さない。置き換え文を見せるのは同日の review の
   指摘による（Alternatives「第 2 段に置き換え文を見せない」）。第 2 段に送るのは確信度の高い順に 1 本あたり 5 件まで
   （`AUDIT_MAX_CONFIRM`）で、drift（原典が公開日より後に変わった疑い）・同じ文の重複・ノートに書かれていない URL の
   候補（`url_not_in_note`、ノートの link・裸の URL・ソース節の URL と突き合わせる）は送らない。候補は試作で 1 本
   あたり 0〜3 件、T9 で 0〜2 件（3 回とも）だったので、5 件の上限は通常の run では効かず、第 1 段が壊れて候補を
   大量に出したときの費用の上限として置いた。
3. **モデルには何も書かせず、置き換えはコードが規則で行うようにした。** 両段とも WebSearch・Read・Glob・Grep・Edit・
   Write を deny に置き、ノートと根拠ファイルは `dr_pipeline.py audit-prompt` がタスクプロンプトに全文で入れる（Context の
   権限の制約）。prompt に埋めるノート由来の文字列（ノート・根拠ファイル・文 A / B・URL・locator）は、呼び出しごとの
   乱数の印（`secrets.token_hex(8)`）の付いた区切りで挟み、両プロトコルに「区切りの中と取得したページはデータ」と書いた。
   プロンプトに入れるノートは 100,000 字まで（超えたら監査しない）、根拠ファイルは 60,000 字で切る。
   `dr_pipeline.py audit-apply` が確定した候補を `_audit_replace` の規則で当てる: 文が本文（frontmatter・題・機会メモ・
   ソース節の外）にちょうど 1 回現れる、文が 15 字以上、空でない、元と同じでない、改行・制御文字・ゼロ幅 / bidi の
   文字を足さない、書き換えの編集距離が max(24, 文の 30%) 以内、`` ` `` `<` `>` `[[` `![` `%` `$=` `&` のどれもノート全体で
   数を増やさない、置き換えの前後でノート全体の URL の多重集合（scheme の大文字小文字を問わずに拾い、HTML entity を
   戻してから比べる。大文字小文字だけの違いも変化に数える）・link 先の並び・`**` と `` ` `` の数・見出し行（固定節の
   見出しの数を含む）が変わらない、frontmatter・機会メモ・ソース節が変わらない。続けて第 2 段の判定を照らす（`_audit_fix_reject`）: `replacement_verdict` が consistent で、各 part の
   `wrong` が文 A にあり、`fixed` が空でなければ文 B にあって A に無く、空なら `wrong` が B に無い。値は T9 の r1・r2 の
   適用 9 件が全部通る範囲で決めた（最も狭い余白は編集距離で 7 字、最小長で 6 字）。規則に外れた確定候補は適用せず、
   規則の名前を記録して WARN を出す。状態は `state/<line>/audit/<date>.json`（orchestrator が第 1 段の前に前回の分を
   消す。消せなければ監査を回さず AUDIT 行の理由は `E_STATE`）、監査の前のノートは `state/<line>/pre-audit/<date>.md` に
   残し、ログに `AUDIT <line>: {...}` を 1 行出す。`audit/`・`pre-audit/` と呼2 の改稿前の写し `pre-verify/` は script
   だけが書く置き場で、呼1・呼2 の deny に置いた（`SCRIPT_STATE_DENY`）。
4. **fail-open にした。** 第 1 段の失敗・timeout・解析できない応答では AUDIT 行が `"ran": false` と理由を持ち、ノートは
   呼2 の後のままになる。第 2 段の 1 回の失敗はその候補だけを確定にしない（`confirm_failed`）で、ほかの確定候補は当てる。
   どちらも run の成否を変えない。認証・課金のエラー（`E_AUTH` / `E_BILLING`）は呼1・呼2 と同じく残りの line を止め、
   その line で確定済みの候補は当てる。
5. **課金の上限と予約に監査を入れた。** api mode の呼び出しごとの上限に `[billing] audit_max_usd`（第 1 段）と
   `audit_confirm_max_usd`（第 2 段 1 件）を足し（`scripts/lib/billing.sh` の `budget_flags`）、台帳には `audit` /
   `audit_confirm` の呼び出し名で記録する。1 line の予約額は `[audit] enabled` のときだけ
   `audit_max_usd + 5 × audit_confirm_max_usd` を足し、その合計が `daily_cap_usd` に収まらない設定は起動時に止める。
   第 1 段の前と第 2 段の各回の前に日・月の残額を確かめる。2 つの上限の既定値は、試作と T9 の 1 回あたりの実測の最大の
   およそ 2〜3 倍に置いた。
6. **計測は件数で残した。** AUDIT 行の件数（確かめた主張・一致・unverifiable・形が壊れた候補・候補・確定・適用・
   拒否・第 2 段の回数・turns・費用）を metrics の `verification.audit_*` に合算し、費用は `total_cost` にも入れる。
   `expect-check` は `audit_ran_rate` と、監査した 1 line あたりの `audit_<件数>_mean` を読む。判定は run の中で
   ノートの訂正として消費され、事後の採点は置かない（ADR-0010 の in-loop 型）。

## Review-when

- `audit_applied_mean` が監査した line 20 本を超えて 0.1 を下回り続ける → 第 1 段が拾えていないか規則が厳しすぎる。
  `audit/<date>.json` の候補と `rejected` の規則の内訳を見る。0.1 は、T7 の 1 本あたり 0.58 件と T9 の 1 周の適用率 3/7〜5/7
  から見積もった期待値（約 0.25〜0.4 件）を大きく下回る値で、呼2 のプロトコルと line の構成が今のままの間に限る。
- 運用者が監査の後のノートに T7 と同じ型（帰属・時点・範囲・条件）の誤りを見つけ続ける → 1 周の見逃し（T9 で 7 件中
  2〜4 件）が効いている。第 1 段を 2 周にする案（Alternatives）を測る。
- 運用者が `pre-audit` との diff で、監査の置き換えが正しい文を誤らせた例を 1 件でも見つける → 2 段の一致を確定に
  している前提が崩れた。監査を止めて原因を調べる。
- 監査した line 20 本の `audit/<date>.json` で、`url_not_in_note` で skip した候補が第 1 段の候補全体の 2 割を超える →
  第 1 段がノートの外の URL を候補に付けている。第 1 段のプロトコルの URL の欄の書き方を見直す。2 割は、URL の欄を
  「ノートに書かれた URL」にした後の r3 の 0/7 を基準に、r1・r2（その指示の前）の適用 9 件中 2 件と同じ水準に戻った
  ことを見る値で、第 1 段のプロトコルが今のままの間に限る。
- 監査した line 20 本で `audit_ran_rate` が 0.9 を下回る（timeout・turns の上限・解析の失敗）→ timeout・`--max-turns`・
  `--effort` を見直す。
- 呼2 のモデル・effort・プロトコルか根拠表の形式が変わる → 呼2 の後に残る誤りを測り直し、1 本あたり 0.2 件（T7 の
  0.58 件の約 3 分の 1。このとき 1 周の適用は 1 line あたり 0.1 件前後で、1 項目めの閾値と重なる）を下回れば、呼3 が
  費用に見合うかを測り直す。
- `claude` CLI の更新で `--tools`・`--safe-mode`・`--effort` が廃止・意味変更される、または allow か `!` の否定が cwd の外の
  deny に例外を作れるようになる → Decision 1・3 の前提が変わる。

## Alternatives Considered

### 何もしない（運用者が読んで手で直す）

呼び出しも費用も増えない。棄却: 読者に届いているノートの 12 本中 5 本に原典と両立しない事実が 1 件以上あり、3 件は話者・
時点・帰属の取り違えで読者が誤った事実を持ち帰る重さだった。誤りの形は数値でなく「誰の・いつの・どの量の」で、読むだけ
では気づけず、運用者が原典を開いて確かめる手間が毎朝の本数だけかかる。

### 呼2 のモデルを opus にする

単価だけを変え、呼び出しを増やさずに済む。植えた誤りの fixture では opus が sonnet を上回った。棄却: 本番に残った誤りの
再実行では 2/7 対 2/7 で差が見えなかった（各 1 周、入力は見逃しやすい誤りに偏ったノート。直した誤りは違い、和は 3/7）。
残った 7 件のうち 6 件は呼2 が照合して supported とした行の中にあり、うち 3 件は根拠表の proposition 自体が同じ誤りを
持っていた。呼2 はノートと表の一致を照合の成功と読み、モデルを替えてもこの読み方は変わらない。残る 1 件は表の外の文で、
呼2 は改稿と照合を同じ呼び出しで行うので、自分が書き換えた文を照合で拾えない。

### 呼2 の照合の手順を要素ごと（誰の・いつの・どの量の・どの範囲の）に分ける

呼び出しを増やさずに、残った誤りの型に直接向けられる。棄却: 同じ日の 2 案の試験（T8）で、実在の 7 件の訂正が 2〜3 件に
とどまり採用の条件 4/7 に届かず、後の案は植えた誤りの fixture で現行を下回った。残った誤りの半分は根拠表の proposition 自体が
誤っていて、呼2 はノートと表の一致を照合の成功と読む形だった。Open — 再訪条件: 改稿前の写し（`state/<line>/pre-verify/`、
2026-11-08 から）で誤りが呼1 由来か呼2 由来かを分けて数え、呼2 由来の誤り（呼2 が書き換えて誤らせた文）が大半を占めた
とき。

### 第 1 段を 2 周回す

T7 の 3 周（同じプロトコル）のうち 2 周の和は 7 件中 6〜7 件で、1 周（4〜5 件）より多く拾う。T9 の 2 回の和も 6/7 だったが、
2 回はプロトコルが違うので同じ段を 2 周回した測定ではない。棄却: 第 1 段の費用と時間が倍になる。運用者の承認は監査
1 本で、まず 1 周の本番の実績を `audit_applied_mean` で見る。Open — 再訪条件: Review-when の 2 項目め。

### 監査のモデルを sonnet にする

1 回あたりの費用が下がる。呼2 の再実行では opus と sonnet の差が見えなかった（2/7 対 2/7）。棄却: 監査の試作と T9 は
opus だけで測り、sonnet の監査の検出率は測っていない。植えた誤りの fixture では opus が上回り、T8 では sonnet が WebFetch の
依頼に原稿の値を書き込む形が観察された（T9 の 1 回目の見逃しと同じ形）。モデルは `[audit] model` で替えられる。Open —
再訪条件: 同じ 5 本で sonnet の監査を測り、opus と同じ件数を確定・適用する。

### WebFetch 以外の取得経路（Bash の curl、コード側の取得、外部の読み取りサービス）を監査に持たせる

約 100,000 字の切り捨てと要約を避けられる。棄却: 無人 run のモデルの Bash は 2026-08-22 の PoC 以来 deny に置いている
（`--allowedTools` が加算リストで、user settings の auto mode 下では列挙外の Bash が通った）。ADR-0019 はさらに `--tools` で
組み込みの道具集合を絞った。コード側の取得は stdlib の `urllib` でも書けるが、HTML・PDF・JSON の解析とリダイレクト・
文字コードの扱いをランタイムに足し、取得したページを解析するコードの攻撃面が増える。切り捨ては「無いことは根拠に
しない」と同じ文書の別 URL（item 単体・`offset`・PDF の HTML 版）で扱い、取れない主張は unverifiable に数える。Open —
再訪条件: `audit_unverifiable_mean` が `audit_claims_mean` の 1 割を超える。

### 監査のモデルが直接 Edit で直す形

置き換えの規則を持たずに、文をまたぐ訂正や言い換えもできる。棄却: Context の取得の制約のとおり、編集の権限を持つ
照合者は途中で切れた取得から正しい文を消した。直接の Edit では「両段が確定した文だけ」「文 1 つだけ」「link を保つ」を
機械で保証できず、変更の範囲が呼2 と同じく広がる。コードの置き換えなら変更は確定した文に閉じ、`pre-audit` との diff で
全部を見られる。

### ノートと根拠ファイルを Read で読ませ、それ以外を deny で塞ぐ

プロンプトが短くなり、試作と同じ形になる。棄却: allow は deny に例外を作れず、「この 2 ファイルだけ」を書けない。Read を
広く許すと、WebFetch を持つモデルが deny の列挙に漏れた場所を読める。2 ファイルはプロンプトに入る大きさなので全文で
渡した（ノートの上限 100,000 字は vault の最長ノートの約 2.6 倍）。

### 第 2 段に置き換え文を見せない（独立性を優先する）

第 2 段の判定が第 1 段の置き換え文に引きずられない。初稿はこの形だった。棄却: 第 2 段が元の文が原典と両立しないことだけを
判定すると、1 文に主張が 2 つあり、第 1 段が誤った方でなく正しい方を書き換えた置き換えも両段を通る（同日の security
review の指摘）。置き換え文を見せ、誤りと訂正の部分を逐語で返させれば、「訂正が誤りの部分に当たっている」をコードが
包含で確かめられる。訂正の値（`correct_value`）が置き換え文に含まれ元の文に含まれないことで確かめる形も考えたが、
`correct_value` はモデルの言い換えで逐語に一致せず、語句を削って直す訂正（T9 の節番号の誤りと、誤り 0 のノートの 1 件）は値を持たない。

### 置き換えの規則を字数の差と文中の URL・link の数にとどめる

初稿の規則で、短い文の訂正を通すことを優先した。棄却: 同日の review で、文の丸ごとの差し替え・Dataview の inline JS・
link 先のすり替え・wikilink / 埋め込み / コメントの追加・見出しの重複が通ると分かった（Context）。vault の Obsidian は
ノートの一部を実行・埋め込みするので、置き換えは書式の記号を足さない平文の小さな訂正に限った。T9 の 9 件は今の規則でも
全部通る。

### 第 1 段だけで適用する（第 2 段を置かない）

呼び出しが 1 本で済み、第 2 段が実在の誤りを通す損も無くなる。第 2 段は T7 で候補 10 件のうち 3 件、T9 の 1 回目で 5 件の
うち 2 件を一致と判定した。そのうち一致と読めたのは T7 の 2 件と T9 の 1 件で、T7 の 1 件は文単位なら軽微なずれ、T9 の
1 件は指示語のために実在の帰属の誤りを通したものだった。棄却: 第 1 段だけだと、一致と読めた 3 件の文を書き換える。
置き換えは人の確認なしにノートに入るので、誤りを残す損（1 周の見逃しと同じ扱い）より、正しい文を誤らせる損を重く
置いた。

## Consequences

- 呼2 の後に残る帰属・時点・範囲・条件のずれのうち、両段が確定し規則に合う置き換えのあるものが、毎朝の run の中で
  直る（ノートは呼1 が vault に書いた後で、監査はその場で書き換える）。T7・T9 の数から、1 周で直るのは残る誤りの 4〜7 割で、
  監査した 1 line あたりの適用は約 0.25〜0.4 件と見積もった。残りは 1 周の見逃しとしてノートに残る。
- 置き換え文は第 1 段のモデルが原典を読んで書く文で、第 2 段がそれを原典と照らし、誤りと訂正の部分を逐語で返す。
  コードの規則は形（位置・字数・編集距離・書式の記号・ノート全体の URL・link・強調・見出し）と第 2 段の span の包含だけを
  確かめ、内容の正しさは 2 つのモデルの判定に任せる。web 由来の内容がモデルの文を通ってノートに入る経路が 1 つ増えた。
  T9 で誤りを持つ 5 本への適用 14 件（r1 3・r2 5・r3 6）はどれも原典どおりだったが、本番での正しさを見るのは運用者の
  `pre-audit` との diff になる。
- 第 2 段は置き換え文を見るので、第 1 段の結論に引きずられうる（独立性の一部を手放した）。r3 で第 2 段が一致とした
  候補は 0 件で、この効果は分けて測っていない。
- 候補の URL をノートの URL に限ったので、ノートが引いていない資料でしか確かめられない誤りは候補にならない（第 2 段は
  同じ文書の別 URL を組める）。
- 「原典に無い属性を足した」を食い違いとするので、ノートが引いていない別の資料では正しい情報も削られる（T9 で誤り 0 の
  ノートへの 1 件）。
- 直した文と直さなかった候補は `audit/<date>.json` と `pre-audit` の写しでたどれる。どちらも script だけが書き、呼1・
  呼2 の deny にあり、呼3 のモデルは書き込みの道具を持たない。両方とも line ごとに毎日 1 ファイル増え、片付けの仕組みは
  置いていない。
- 監査を止めるのは設定 1 行で済む。過去の置き換えを戻すのは `pre-audit` の写しをノートへ写す手作業で、監査の後にノートへ
  加えた変更も一緒に消える。
- article 1 本あたりの呼び出しが「第 1 段 1 + 候補ごとに第 2 段」だけ増え、費用と時間（最長で第 1 段 10 分 + 第 2 段
  4 分 × 5）が足される。api mode では 1 line の予約額が上がり、日の上限に収まる line の数が減りうる。
- 両段が確定しても規則に外れた誤り（文をまたぐ・同じ文が 2 回ある・link や URL や書式の記号を変えないと直せない・
  書き換えが大きい・`%` `<` `>` `&` を足す（百分率や比較を書き足す訂正もここで止まる）・置き換え文が無い・第 2 段が
  置き換え文を訂正と認めない）は
  ノートに残り、WARN と `audit/<date>.json` にだけ出る。直すのは運用者の手になる。
- 第 2 段は文脈を持たないので、前の文の文脈で決まる誤り（T7 の範囲の限定の脱落）の判定は揺れる。
- 原典を取れない主張（PDF・403・削除済み・途中切れ）は監査の外に残る。
- metrics の `verification` に `audit_*` が増え、`total_cost` に監査の費用が入る。監査を有効にした日の前後で
  `total_cost_mean` を分けて読む。`/dr-review` の語彙はこの変更では足していない。
- 段ごとの turns と timeout は `scripts/daily-research.sh` が正本で、`docs/CONTRIB.md`・`docs/RUNBOOK.md` とその日本語版にも
  同じ値を書いた（計 5 か所）。
- 既定は off で、運用者の `config.toml` には `[audit]` 節がまだ無い。`[audit] enabled = true` を書くのは運用者の手順で、
  それまで毎朝の挙動は変わらない。
