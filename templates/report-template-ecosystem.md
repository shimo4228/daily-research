# {topic_title}

（本文は自由形式の散文。**固定見出しは置かない** — 必要なら内容に合わせた見出しを 1〜2 個まで。
流れの目安は 何が公開・更新されたか → 実装は実在するか、観測対象の技術をコードや依存関係で実際に
使っているか → 位置づけ（単なる router / judge / plugin か、新しい制御基盤か）→ 実測（速度・価格・
精度・大規模モデル呼び出しの削減）と、不確実性・誤判定・フォールバックの扱い → いま試せるか →
確認済みの事実と将来性についての推論の区別、を段落で。材料が無い項目は飛ばす — 埋めるために
推測を足さない。記述規律は 3 点:

1. **冒頭はエコシステムで起きた出来事から**: 第一文は今回観測した変化（公開・release・commit・
   測定・停止）で始める。過去レポートや過去 run の仮説から書き始めない。運用者の既存ツールへの
   導入提案・承認要求・「〜すべき」・手順の列挙は書かない。
2. **初見の読者向けに**: 登場する概念・プロジェクト名は初出時に平易に。過去レポートや watchlist は
   座標だけで参照しない — 中身を 1 行要約して運ぶ。前回報告済みの内容の再説明は 2 文まで。
3. **全 claim に as-of 日付、source の主張 / 推論を文の形で分ける**: 公開日と出来事の日付を区別する。
   一次ソースを WebFetch で確認済みの事実だけを事実として書き、二次情報は「〜と報じられている」と
   区別する。宣伝上の主張は「作者は〜と述べている」と書き、実装や測定で確認できた範囲と分ける。
   将来性は「〜なら〜になりうる。未確認なのは X」の形で条件付きに。括弧の認識論注記は 1 本あたり
   2 箇所まで。

長さは article が本文 3,000 字以内で材料に応じて短く、brief が 300〜600 字。末尾の「機会メモ」
「ソース」の 2 節だけは下記の固定見出し・形式で書く — 機械検査 (ctl-016) の対象である。）
